# Сборка и зависимости

- **Версии, которые пока держим:** eslint и `@eslint/js` - на 9, пока `eslint-plugin-import`, `eslint-plugin-react` и `eslint-plugin-jsx-a11y` не поддержат eslint 10; TypeScript - на 6.0, пока `typescript-eslint` не поддержит 7 (в пакете TypeScript 7 нет классического API компилятора). `tsconfig.json` - `moduleResolution: "bundler"` без `baseUrl`, `strict` без поблажек плюс `noImplicitReturns`, `noFallthroughCasesInSwitch` и `isolatedModules` (код компилирует swc по одному файлу), `noEmit` - `tsc` только проверяет типы. Объявления типов (`.d.ts`) - только в корневой `typings/`. Код сборки (`webpack.config.ts`, `webpack/`, `scripts/`) проверяет отдельный `tsconfig.node.json` с типами Node: `lint:tsc` запускает оба, поэтому в `src` типов Node нет. Eslint проверяет весь репозиторий (`lint:src` - `eslint .`) с теми же правилами и берёт типы из обоих tsconfig (`parserOptions.project`); новый `.ts` вне `src` должен попасть в `include` одного из них, иначе хук упадёт с «file was not found in any of the provided project(s)». В `scripts/` разрешён `console` - это вывод консольных программ. TypeScript 6 не подключает `@types/*` сам, поэтому `process.env`, которое подставляет webpack, описано в `typings/process.d.ts`.
- **Конфиг webpack - на TypeScript и по частям.** `webpack.config.ts` только собирает конфиг через `lodash/flow` из функций `webpack/init/*` и `webpack/rules/*` (реэкспорт - `webpack/index.ts`) вида `(опции) => (webpackConfig) => webpackConfig`: `initBaseConfig` (режим, `resolve`, алиасы), `initClientConfig` (вход, выход, плагины), `initDevServer`, `loadScripts` (swc), `loadStyles` (CSS-модули и sass), `loadAssets` (картинки). Общие флаги (`IS_DEVELOPMENT`, `IS_DEV_SERVER`, `CONTENT_HASH`) - в `webpack/consts.ts`, `process.env` для панели - `defineGlobals`, эндпоинт `/dev/obs-connection` - `serveObsConnection`, журнал dev-сервера - `webpack/init/devJournal`. Новая часть конфига - новая функция в `webpack/init/` (настройки и плагины) или `webpack/rules/` (правила загрузчиков) и строка в `flow`, а не правка чужой. Node 24 запускает `.ts` сам, импорты - с расширением `.ts`; пакет - `"type": "module"`, поэтому код сборки и скрипты - ES-модули. По той же причине утилиты lodash в `webpack.config.ts`, `webpack/` и `scripts/` подключаются с `.js` (`lodash/flow.js`, `lodash/find.js`): у lodash нет поля `exports`, и без расширения Node их не находит (`ERR_MODULE_NOT_FOUND`); в `src` webpack подставляет расширение сам, там - без него (`lodash/find`). Алиасы (`__types`, `__utils` и другие) задаются только в `paths` у `tsconfig.json`, webpack берёт их оттуда через `tsconfig-paths-webpack-plugin`.
- **Кэш и минификатор сборки.** Кэш - `cache: filesystem` в `node_modules/.cache/webpack`, стенд задаёт для своих сборок отдельную папку переменной `WEBPACK_CACHE_DIRECTORY`. У каждого режима своя папка (`CACHE_NAME`): настройки swc у dev-сервера другие, а имена правил те же, и общий кэш отдал бы не тот код. Значения `DefinePlugin` кэш учитывает сам: сборка с `TEST_UPDATE_SERVER` не попадает в обычную (проверено). В CI кэша нет, выпуски собираются начисто. Если сборка ведёт себя странно после обновления инструментов - удаляем эту папку. Минификатор - swc через `minimizer-webpack-plugin` (его же webpack использует по умолчанию с terser): первая сборка 6 с вместо 14 с. Выдаёт синтаксис до ES2022, а минимальный Chromium в `config/compatibility.json` - 103, его поддерживает; поднимая `target` или меняя минификатор, сверяем с этой версией. CSS сжимает `sass` в режиме production, минификатор его не трогает. Папку `build` чистит `output.clean`.
- **Node.js - минимум 24**: `.nvmrc` (по нему ставит Node и GitHub Actions) и `engines` в `package.json` (`^24 || >=26`: нечётную 25 исключает http-proxy-middleware из webpack-dev-server). Это наше решение, зависимостям сейчас хватает 22.22.1 (lint-staged, react-router), поэтому ниже 24 не опускаем. Меняем версию - в `.nvmrc`, `engines`, README и `docs/DEVELOPMENT.md`.
- **Каждое обновление пакетов - с проверкой минимальной версии Node.** После любого `npm install`/`npm update`, который меняет `package-lock.json`, просматриваем `engines.node` всех пакетов в `package-lock.json` (включая вложенные и dev) и находим самое строгое требование: самую высокую нижнюю границу и исключённые ветки. Если оно строже нашего `engines` (выше 24 или исключает поддерживаемую нами ветку), в том же изменении поднимаем минимум в `engines`, `.nvmrc`, README и `docs/DEVELOPMENT.md`, пишем в пункте выше, какой пакет его задаёт, и проверяем на новой минимальной версии из `nvm` (запуск её `node.exe` напрямую, без `nvm use`): `npm run build:prod`, `npm run package:release`, `npm run lint`, dev-сервер. Если пакет перестал поддерживать и 24 - сначала обсуждаем с пользователем: откатить пакет или перейти на новую ветку Node в `.nvmrc`. Результат проверки - что нашли и подняли ли минимум - пишем в ответе.
