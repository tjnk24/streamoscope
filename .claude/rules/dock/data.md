# Панель: данные, стор, сервисы и роутинг

Как устроены обновления, плашка моста, диагностика, вход и моки - `docs/internals/dock.md`, читаем перед правкой этих частей.

- **Состояние - в Redux Toolkit.** Общие слайсы в `src/reducers`: `connection` (статус соединения, код последнего закрытия, версия OBS, текущая коллекция сцен), `stats` (найденные выходы и данные карточек), `update` (последний выпуск, состояние проверки, обновлятор и статус от моста, запрос установки `request` с версией и временем), `@localStorage/settings` (сохраняется в localStorage мидлварой из `store.ts`).
- **Слайсы страницы - в `pages/<Страница>/reducers`, только если состояние нужно одной странице** (решение пользователя: в общие выносим, когда понадобится другим). Корневой редьюсер собран `combineSlices` в `src/reducers/index.ts` (`rootReducer`), страница подключает свои слайсы сама, все одним вызовом (решение пользователя: у страницы может быть и 20 слайсов): `export const injectedSlices = injectSlices({releaseNotesModal: releaseNotesModalSlice, releaseNotes: releaseNotesSlice})` в `reducers/index.ts` страницы (`utils/redux/injectSlices` вызывает `injectInto(rootReducer)` у каждого), так общие редьюсеры о ней не знают. Тип результата - `InjectedSlicesDto` из `__types/app/slices`: в нём точные `reducerPath` и `selectSlice` каждого слайса, потому что `ReturnType` от `injectInto` расширяет имя слайса до `string`. Экшены - `actions` в `actions.ts` страницы, одним вызовом `export const actions = bindSliceActions(injectedSlices)` (`utils/redux/bindSliceActions`: `bindActionCreators` со `store.dispatch` у каждого слайса), обращение - `actions.<слайс>.<экшен>`, селектор слайса - `injectedSlices.<слайс>.selectSlice` в `selectors/<слайс>Selectors.ts` страницы, по файлу на слайс, как общие в `src/selectors` (решение пользователя): он отдаёт начальное состояние, пока слайс не получил ни одного экшена. Модалки: слайс `{isVisible, ...данные}` с `setData` и `reset`, родитель рендерит модалку только пока `isVisible`, закрытие вызывает `reset` (`pages/Stats`: `adviceModal`, `pages/Settings`: `releaseNotesModal`). Данные с сервера (решение пользователя): слайс запроса `createRequestSlice<Данные>(имя)` из `utils/redux` (`{status, data, error}`, `RequestStateDto` и `RequestStatusEnum` из `__types/api/request`; экшены `pending`, `success`, `failed`, `reset`), загружает их метод сервиса страницы, вызывая лоадер с параметрами прямо в вызове (`releaseNotesService.handleRequest = () => releaseNotesLoader({per_page: 30})`), а разбирает ответ мемоизированный селектор (решение пользователя: в сервисе - только вызов лоадера, обработка данных - в отдельном селекторе). Параметры запроса пишем прямо в этом вызове, константами из `preload` или контейнера их не передаём. `preload` (`utils/hocs/preload`) вызывает метод сервиса в `onLoad` и сбрасывает слайс в `onDispose`; статус компонент сам не сравнивает: флаги дают селекторы статуса (ниже, в правиле о селекторах). Лоадер - `createLoader(actions.<слайс>, <api>.<метод>)` из `utils/redux` в `loaders/<что>Loader.ts`: принимает параметры запроса, вызывает `pending`, метод API, затем `success(ответ как есть)` или `failed(текст ошибки)` и ничего не бросает; о сервисах не знает, сервис в создание лоадера не передаём. Разбор ответа для разметки - селектор в `selectors/` страницы через `createSelector` (`parsedReleaseNotesSelector`: `parseRelease` и фильтр черновиков, предвыпусков и тегов без версии); компонент берёт флаги из селекторов статуса, а данные - из селектора разбора. Слайсы страницы читают компоненты через `useSelector`; если понадобится читать слайс страницы вне React (`selectSlice(getStore())`), тип стора о нём не знает - корневой редьюсер тогда собираем `withLazyLoadedSlices<...>()` с `WithSlice` этого слайса.
- **HTTP-запросы - только через `src/api`** (решение пользователя: схема из транспортов и API-классов, не привязанная к одному сервису). Библиотека - `ky` (поверх `fetch`; выбрана вместо axios: наследование транспортов через `extend`, хуки, типизированные ошибки). **Транспорт** - как говорить с сервером: `utils/api/baseTransport.ts` (`ky.create`, общее для всех: хук `beforeError` пишет любую ошибку запроса в журнал, `source` - `api`, текст ошибки ky уже содержит метод и адрес) и транспорт на каждый внешний сервис через `baseTransport.extend` (`github/transport/githubTransport.ts`: `baseUrl` и заголовки GitHub); токены, свои хуки и прочее для одного сервиса - только в его транспорте. **API-класс** - что спрашивать: наследует `BaseApi` (`utils/api/BaseApi.ts`, транспорт приходит в конструктор, методы на все виды запросов ky (решение пользователя, заведены сразу): `get` и `query` (`<Результат>`), `post`, `put`, `patch`, `delete` (`<Результат = null>`) отдают разобранный JSON, `head` - сам ответ (заголовки и статус); пустое тело (например 204) даёт `null`, а не ошибку разбора: оба базовых транспорта (`baseTransport`, `devTransport`) разбирают JSON через `parseJson: parseJsonBody` из `utils/api`), методы - стрелочные поля класса, наружу - экземпляр (`export const releasesApi = new ReleasesApi()`). API-класс - только HTTP: эндпоинт, параметры и сырой тип ответа, ответ отдаёт как есть. Параметры запроса (query, части пути, тело) в API-класс не зашиваем (решение пользователя): метод принимает их типизированным аргументом (`getList = (searchParams: GithubReleasesQueryDto) => this.get<...>(GITHUB_ROUTES.RELEASES.INDEX, {searchParams})`; аргумент называем как поле опций ky - `searchParams`, `json`, - чтобы передавать его сокращённо, решение пользователя; тело метода API - всегда с новой строки после `=>` с отступом, даже короткое: `getList = (searchParams: ...) =>` и ниже `this.get<...>(...)`, так же `getLatest` и `BaseApi.get`, решение пользователя), значения пишет метод сервиса прямо в вызове (`releaseNotesApi.getList({per_page: 30})`); эндпоинты - в `src/routes/api/<api>.ts` объектом того же вида, что роуты приложения `ROUTES` (`src/routes/app.ts`), файл назван в честь API (`GITHUB_ROUTES` в `routes/api/github.ts`: `RELEASES.INDEX`, `RELEASES.LATEST`), API-классы берут их оттуда, а не из `consts.ts` (решение пользователя); эндпоинт с частью пути - функция в этом объекте (`` RELEASE: (releaseId: string) => `releases/${releaseId}` ``). **Сервис** - что делать с запросом и ответом (решение пользователя): класс с экземпляром, его методы-обработчики (`handleRequest`) вызывают лоадер или метод API с параметрами прямо в вызове; если ответ идёт в Redux - через лоадер, а разбор для разметки делает селектор; если результат нужен самому сервису или другим сервисам - сервис сам разбирает ответ, решает особые статусы и возвращает наши DTO (`updateService.fetchLatest`). Раскладка по тому, кто пользуется (решение пользователя): API, сервис и лоадер, нужные одной странице, - в её `api/`, `services/`, `loaders/` (`pages/Settings`: `api/ReleaseNotesApi.ts` со списком выпусков, `services/releaseNotesService.ts` - вызов `loaders/releaseNotesLoader.ts`, слайс `releaseNotes` - сырой ответ, `selectors/releaseNotesSelectors.ts` - `parsedReleaseNotesSelector`); нужное нескольким местам или общим сервисам - в `src/api`, `src/services` (`api/github/ReleasesApi.ts` - только `getLatest` для `updateService`, который сам разбирает ответ, а 404 через `isHTTPError` считает «новых версий нет»; строка о 404 в журнале остаётся). Раскладка - папка на сервис: `src/api/<сервис>/{<Что>Api.ts, transport/{<сервис>Transport.ts, consts.ts}}` (решение пользователя: транспорт и его настройки - в своей папке `transport/`), в `consts.ts` - базовый адрес и заголовки этого сервиса; Тип сырого ответа берём из пакета типов сервиса, если он есть (GitHub - `@octokit/openapi-types`, `GithubReleaseDto` - `Pick` нужных полей из `components['schemas']['release']`, чтобы тестовые данные не требовали всех полей), иначе пишем свой DTO в `src/types`; сырые типы ответа живут в API-классе, в слайсе с сырым ответом и в селекторе разбора (или в сервисе, который разбирает ответ сам), а компоненты получают из селектора только наши DTO; а тип параметров запроса (`GithubReleasesQueryDto` из `operations` octokit) - тип аргумента метода API, двойник-DTO под него не заводим. Компоненты и `preload` вызывают методы сервиса и читают слайс, API и лоадеры напрямую не вызывают. Импорты не должны замыкаться: `src/reducers` и `store.ts` ничего из `src/api` и `utils/api` не импортируют (`baseTransport` тянет журнал, а он - стор). Тест API-класса - `tests/` рядом с ним: `fetch` подменяет `vi.stubGlobal` (ky читает его при каждом запросе), журнал - `vi.mock`; для ошибки берём статус без повторов (403, 404), иначе ky повторит запрос; тест сервиса - в его `tests/`, API и экшены страницы подменяет `vi.mock`. Запросы к dev-серверу - тоже через слой: `src/api/dev` (`DevApi`: `getObsConnection`, `sendJournal(body)`, `openJournalFolder`; эндпоинты - `DEV_ROUTES` в `src/routes/api/dev.ts`, `BaseApi.post` для POST). Транспорт у него свой - `ky.create({baseUrl: '/dev/'})` без `baseTransport` и его хука журнала: иначе каждая неудачная отправка журнала при выключенном dev-сервере писала бы в журнал новую строку, и так по кругу. Dev-код не должен попадать в production-сборку: вызов `fetchDevObsConnection` стоит прямо в ветке `if (process.env.IS_DEV_SERVER)` (не в отдельном поле класса, иначе сборка его не вырежет), а `new DevApi()` и `ky.create` помечены `/*#__PURE__*/`; после правок проверяем, что в бандле `build/` нет строки `/dev/`. Вне слоя остаётся только obs-websocket (`obsConnectionService`).
- **Экшены без алиасов.** Общие слайсы - `commonActions` из `__actions` (`src/actions.ts`), импортируются под этим именем: `import {commonActions} from '__actions'`. У страницы со своими слайсами - `actions` в её `actions.ts`: `import {actions} from '../../actions'`. `bound as actions` и подобные переименования при импорте не пишем. Общие слайсы перечислены в `commonSlices` (`src/reducers/index.ts`), а `commonActions` собирается так же, как у страниц: `bindSliceActions(commonSlices)` в `src/actions.ts`.
- **Формат настроек - с версией и миграциями.** В сохранённых настройках есть номер `settingsVersion`; настройки без номера считаются версией 1. При загрузке `storageService` прогоняет их по цепочке функций перехода N -> N+1 до текущей версии и сохраняет. Поменял формат настроек (переименовал поле, поменял тип или смысл, разделил одно поле на несколько) - подними версию и допиши функцию перехода, которая переносит выбор пользователя, и тест на неё. Новое поле со значением по умолчанию миграции не требует. Функции перехода не удаляем никогда: кто-то обновится прямо с той версии. Настройки, которые не разбираются или пришли из более новой версии, откладываем и берём значения по умолчанию.
- **Селекторы, которые только достают поля, - плоские, без `createSelector`**, производные данные для разметки - в теле компонента. Исключение (решение пользователя) - селектор, который собирает из стора новые данные, например разбирает ответ API (`parsedReleaseNotesSelector`): его пишем через `createSelector` из `@reduxjs/toolkit`, иначе он на каждом вызове отдавал бы новый массив и перерисовывал компонент на каждое изменение стора. Статус запроса в компоненте не сравниваем (решение пользователя): на каждый нужный компоненту статус - селектор `<слайс>Is<Pending|Success|Failed>Selector` через `createSelector` над селектором слайса и общую утилиту `checkPending`, `checkSuccess` или `checkFailed` из `utils/redux`, которая сама принимает объект слайса и достаёт из него `status`, поэтому передаётся без обёртки: `createSelector([releaseNotesSelector], checkPending)` (решение пользователя) (`releaseNotesIsPendingSelector` - `loading` у `Skeleton`, `releaseNotesIsFailedSelector` - сообщение об ошибке, `releaseNotesIsSuccessSelector` - «заметок пока нет» только после удачной загрузки); селектор статуса, который никому не нужен, не заводим (knip).
- **У каждого слайса - селектор слайса** `connectionSelector`, `statsSelector`, `settingsSelector`, `updateSelector` (`state => state.<слайс>`), поля из него берём деструктуризацией. Один селектор в другой не вкладываем (ни `createSelector` ради одного поля, ни `state => updateSelector(state).latest`; исключения - селекторы разбора и статуса выше): слайсы всегда есть и типизированы, отсутствие значения уже `null` в `initialState`, а селекторы только достают поля и ничего нового не собирают, так что запоминать нечего.
- **В компоненте несколько полей одного слайса - одним селектором слайса**: `const {latest, bridge, request} = useSelector(updateSelector);`, а не по селектору на поле. Immer отдаёт новый объект слайса только при изменении, поэтому лишняя перерисовка бывает лишь от полей, которые компонент не берёт; для небольших `update` и `settings` и для компонентов, которые и так зависят от частых полей `stats` (`useItems` берёт `view` и `hardware`), это неважно. Точечный селектор поля (`connectionStatusSelector`, `statsTargetsSelector`, `statsViewSelector`, `settingsPortSelector`) заводим, только когда компоненту из слайса нужно одно поле: так он не перерисовывается от остальных. Селектор, который собирает новый объект (`state => ({a: state.x.a})`), не пишем: он перерисовывает компонент на каждое изменение стора.
- **Сервисы читают стор через селектор слайса**: `const {latest, bridge} = updateSelector(getStore());`, `settingsSelector(state).isMockEnabled`. Перерисовки сервиса не касаются, поэтому точечные селекторы ради него не заводим; точечный селектор, который больше никто не использует, удаляем (knip его покажет).
- **Хранилище - `services/storageService.ts`**: пароль (`loadPassword`, `savePassword`), настройки (`loadSettings`, `saveSettings`) и последние события журнала (`loadJournal`, `saveJournal`). Ключи и безопасное чтение и запись (`private getItem`, `setItem`, `removeItem` ловят исключения `localStorage`) спрятаны внутри; напрямую к `localStorage` больше никто не обращается.
- **Соединение с obs-websocket - `services/obsConnectionService.ts`**, вне React: переход между страницами не рвёт связь и не сбрасывает графики. Компоненты вызывают методы сервиса, а не шлют сообщения сами.
- **Разовые запросы к OBS - `obsConnectionService.sendRequest`**: запрос встаёт в очередь, и сервис сразу запускает внеочередной опрос (`poll`), чтобы команда не ждала до секунды следующей пачки; если прошлая пачка ещё в пути, запрос уйдёт со следующей (`buildBatch`). Пока OBS не ответил на `Identify` (`isIdentified`), `poll` ничего не шлёт: запрос ждёт в очереди первой пачки после входа, а разрыв связи очередь очищает. Ответ отдельно не ждём. Параметр профиля для моста (команды обновления, журнала, открытия ссылки) пишет `obsConnectionService.setProfileParameter(параметр, значение)`: он сам собирает запрос `SetProfileParameter`, вызовы в одну строку.
- **Роутер - `createHashRouter`.** Адреса внутри `#`: обычные пути после Ctrl+R в OBS открыли бы несуществующий файл.
- **Ссылки строит `routerManager`** (`services/routerManager.ts`: `goToStats()`, `goToSettings()`, с `isHref` - только путь для `<Navigate>`), адреса строками не собираем. Роуты приложения - `ROUTES` в `src/routes/app.ts` (импорт `__routes/app`), рядом в `src/routes/api/` - эндпоинты API.
- **Редиректы на вход и обратно - в `components/AppRoute`** по статусу соединения.
