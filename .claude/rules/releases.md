# Выпуски

- **Версия - semver, источник - `version` в `package.json`** (в панель попадает как `process.env.APP_VERSION`). Номер выбирается по самому крупному изменению в выпуске: **major** - ломает установку или настройки (нужны ручные действия, несовместимый скрипт-мост, выше минимальная версия OBS); **minor** - новая возможность (функция, настройка, площадка, язык, карточка); **patch** - исправления и косметика без новых возможностей (иконки, стили, тексты, переводы). Пока версия 0.x, ломающее изменение идёт в minor и обязательно описывается в заметках. 1.0.0 - когда несколько выпусков подряд ничего не ломали и установка с обновлением устоялись.
- **Метка сборки - `webpack/init/getBuildLabel`**: пустая только у сборки `release.yml` по тегу (`GITHUB_REF_TYPE=tag`, его ставит сам GitHub), у любой другой - `git describe --tags --always --dirty --match v*` (`v0.6.0-5-g4420f14-dirty`), вне git - `unknown` (стенд собирает копию проекта без `.git`). Выпуск - только то, что собрал и подписал CI, поэтому метку получает и локальная сборка с коммита выпуска. Номер версии у таких сборок прежний (решение пользователя): по нему сравнивают обновлятор, мост и загрузчики, а суффикс в нём задел бы форматы из обещаний ниже, и Inno Setup требует цифры в `VersionInfoVersion`. Метка только для глаз: `process.env.BUILD_LABEL` (`defineGlobals`) - строка под версией в настройках, версия в диагностике и `build=` в строке журнала `started`; `scripts/buildInstaller` - `/DBuildLabel`, имя `streamoscope-setup-<версия>-local.exe` (`/DSetupName`) и ` (local build <метка>)` в мастере и в «Приложениях».
- **Версия скрипта-моста - целое `BRIDGE_VERSION` в `obs-script/streamoscope-bridge/consts.lua`**, он отдаёт её в JSON как `bridgeVersion`. Повышается, только когда меняется формат его данных или панель начинает рассчитывать на новое поле. Панель и мост переключаются вместе при запуске OBS, но смена коллекции сцен перезагружает скрипты, и новый мост может встретить открытую старую панель: данные моста только дополняем.
- **Требования к окружению - `config/compatibility.json`** (минимальные версии OBS и Chromium). Остальное `scripts/packageRelease` берёт из кода: версию RPC - из `OBS_RPC_VERSION`, версию моста - из `BRIDGE_VERSION`, список запросов - из `ObsRequestTypeEnum`. Подняли требование - правим этот файл в том же изменении.
- **Сборка выпуска - `npm run package:release`**: production-сборка (имена файлов с хэшем содержимого, чтобы OBS не взял старое из кэша) и папка `release/streamoscope-<версия>/` с `dock/`, скриптом-мостом, `updater/`, `configure-obs.ps1` с `ConfigureObs/` (настройка OBS, её запускает деинсталлятор), `LICENSE`, `README.txt` и `compatibility.json`. Папка `release` в git не попадает. Скрипт - `scripts/packageRelease/`: `index.ts` только перечисляет шаги, каждый шаг - своя функция в своём файле (`buildCompatibility`, `copyReleaseFiles`, `writeReadme`, `writeCompatibility`); помощники одного шага лежат с ним в его папке (`buildCompatibility/` с `readNumberFromSource`, `readRequiredRequests`, `readSourceFile` и `index.ts`, который реэкспортирует шаг), текст `README.txt` для пользователя - шаблон `README.template.txt` с подстановкой `{{version}}`.
- **Как выпустить:** заметки `docs/release-notes/<версия>.md` (сначала английский, после `---` русский), затем `npm version <major|minor|patch>` (коммит и тег `v<версия>`) и `git push --follow-tags` - только по просьбе. Тег запускает `.github/workflows/release.yml` из двух заданий. `build` на Windows: проверяет, что тег совпадает с `package.json` и заметки есть, `npm test`, Pester (ставит Pester 5), Inno Setup (если его нет на машине - через choco), `npm run package:installer`, всё из `release/` - в артефакт. `publish` на Linux, только для тега и только после ручного подтверждения (окружение `release` в настройках репозитория: подтверждает владелец, принимает только теги `v*`): обновления доходят до людей без единого клика, поэтому это последняя проверка человеком. Он собирает zip, подписывает minisign установщик, zip и `compatibility.json`, проверяет подписи ключом `minisign.pub` из репозитория, пишет `SHA256SUMS.txt` и создаёт GitHub Release. К заметкам выпуска в конце дописывается скрытая строка `<!-- compatibility: {...} -->` с содержимым `compatibility.json`: панель читает её через API GitHub, потому что сами файлы выпуска странице `file://` недоступны (у `release-assets.githubusercontent.com` нет CORS). Секретный ключ есть только у `publish`. Тот же workflow можно запустить вручную (`workflow_dispatch`, `gh workflow run release.yml`) - тогда только `build`, без выпуска. На каждый пуш в `main` и pull request `.github/workflows/ci.yml` гоняет `npm test` и `package:release` на Linux и тесты Pester установщика и моста на Windows. Версии действий GitHub (`actions/checkout` и другие) держим на последних мажорных.
- **Что вне `versions\`, обновляет только установщик**: заглушку `installer/loader/streamoscope-bridge.lua`, загрузчик панели `installer/loader/index.html`, код деинсталлятора в `installer/streamoscope.iss` (`[Code]`, `[UninstallDelete]`, тексты окон), запасной `configure-obs.ps1` с `ConfigureObs/` в корне, `minisign.exe` и иконку. Фоновое обновление их не трогает. Если выпуск меняет что-то из этого или кладёт новое вне `versions\`, в заметках к нему обязателен заметный блок «запустите установщик один раз» - первым, выделенным, на обоих языках: что изменится, где взять установщик и что настройки не потеряются. Сама панель просит об этом, только пока заглушки нет вовсе (`isInstallerNeeded`: мост не отдаёт `stubVersion`), о других таких изменениях людям скажут только заметки.
- **Срочное исправление вышедшей версии - временная ветка от тега**, постоянной ветки `release` нет (решение пользователя: выпуск и так отмечен тегом, а лишние слияния одному разработчику ни к чему). Если в `main` уже лежит невыпущенное: `git switch -c hotfix/X.Y.Z vX.Y.(Z-1)`, в этой ветке - исправление и заметки `docs/release-notes/X.Y.Z.md`, затем `npm version patch`; пуш ветки с тегом (`git push --follow-tags -u origin hotfix/X.Y.Z`) - только по просьбе. `release.yml` запускается от тега в любой ветке и сам гоняет все тесты, а `ci.yml` на пуш такой ветки не срабатывает. Потом ветку сливаем в `main`, чтобы исправление и заметки не потерялись, и удаляем. Чиним только последнюю вышедшую линию: «последний выпуск» GitHub - тот, что опубликован последним, по нему работают панель, обновлятор и страница выпусков, и 0.6.2 после 0.7.0 вернул бы новые установки на 0.6. Для старой линии понадобился бы `--latest=false` в `gh release create`, в `release.yml` его нет.
- **Обещания старым версиям - навсегда.** Обновление выполняет уже установленная версия, поэтому любая старая (хоть 0.1.0) должна уметь поставить самую новую. Никогда не меняем: формат `current-version.js`, `update-trial.txt`, `healthy-version.txt`, `rolled-back-version.txt` и `healthy-loader.txt` (их читают заглушка `installer/loader/streamoscope-bridge.lua` и загрузчики старых версий, а их обновляет только установщик), путь загрузчика версии `versions/<версия>/streamoscope-bridge.lua` и саму заглушку: она не меняется никогда, кроме ломающего выпуска, верхнюю папку `streamoscope-<версия>` и обязательные файлы (`RequiredPackageFiles`) в архиве выпуска, формат тега `vX.Y.Z`, имена файлов выпуска (`streamoscope-setup-<версия>.exe`, `streamoscope-<версия>.zip`, `compatibility.json` и их `.minisig`), адрес выпусков `https://github.com/tjnk24/streamoscope/releases/download/v<версия>/`, ключ подписи (`minisign.pub`), строку `<!-- compatibility: {...} -->` в конце заметок и формат команды мосту `install:X.Y.Z`. Установщик продолжаем выпускать: версии до 0.5.0 обновляются только через него, и он сам раскладывает папку установки по-новому. В `compatibility.json` и строку совместимости поля только добавляем, существующие не удаляем и не переименовываем. Если без смены чего-то из этого не обойтись (например, ключ скомпрометирован), это ломающий выпуск: старые версии обновятся только вручную, и это пишется в заметках. Так было один раз - в 0.3.0 при переименовании obs-stats-widget в StreamoScope: 0.1.0-0.2.0 ищут файлы под старыми именами и до 0.3.0 сами не обновятся. Переноса со старой установки больше нет: ею пользовался только автор, и он перешёл вручную.
- **Ключ подписи:** публичный - `minisign.pub` в корне репозитория, секретный - только в секрете `MINISIGN_SECRET_KEY` репозитория, без пароля. Секретный ключ не читаем, не выводим и в репозиторий не кладём.
