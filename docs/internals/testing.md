# Как проверять

| Что менял | Чем проверять |
| --- | --- |
| Логику панели | `npm run test:unit`, входит в `npm test` |
| Разметку и поведение панели, обновление React, antd и сборщика | `npm run test:e2e` (Playwright в Docker), входит в CI |
| Панель глазами | `npm run start:dev` или `preview_start` с именем `dock-dev` |
| Журнал без OBS | `npm run start:dev` с включёнными моками, файл `.dev-journal/streamoscope.log` |
| Код моста на Lua, загрузчик, заглушка, откат | `npm run test:bridge`: настоящий LuaJIT из OBS, путь с кириллицей, без самого OBS; судейство пробы загрузчиком 0.6.0 (`harness/loader_0_6_0.lua`) |
| Настройку OBS и обновлятор | `npm run test:installer` |
| Запуск скрипта из `[Code]` установщика | тестовый `setup` вне проекта: константы, типы, внешние функции и `ProcessWindowMessages`…`RunConfigureObs` из `streamoscope.iss`, `SlowScriptMilliseconds` - несколько секунд, `InitializeSetup` запускает свой `.ps1` с быстрым, долгим и 64-битным сценарием, пишет коды в файл и возвращает `False`; запуск с `/VERYSILENT /SUPPRESSMSGBOXES` ничего не ставит |
| Панель в настоящем OBS, поток, обновление и откат | тестовый стенд, `npm run test:stand` |

## E2e панели (Playwright)

- **Что проверяет**: production-сборку из `build/` по `file://`, как OBS, на ширине 300 и 670 px (проекты `dock-300` и `dock-670` в `playwright.config.ts`). Спеки - сценарии пользователя:
  - `stats/stats` - подключение к мокам, тост, пустые карточки до эфира, карточки в эфире, снимки и ARIA-снимок; `stats/platformChoice` - выбор VK Видео, OK или Boosty на карточке общего сервера меняет её заголовок; `stats/cardOrder` - перетаскивание карточки за ручку (dnd-kit) меняет порядок, и он остаётся после перехода в настройки;
  - `settings/settings` - все группы раскрываются, снимок без «Обновлений»; `settings/display` - свитчи карточек прячут и возвращают карточки, снятая галочка убирает строку из всех карточек, русский язык сразу в шапке, плашке и карточках, светлые цвета (снимок); `settings/connection` - порт вне диапазона и пустой пароль не уходят, ошибка под полем; `settings/updates` - «Check for updates» с подменённым ответом GitHub (`page.route` на `releases/latest` с CORS-заголовком: страница `file://`) для текущей и более новой версии, включение автообновления сразу проверяет GitHub, «What's new» рисует markdown заметок текущей версии (markdown-to-jsx: заголовок, список, ссылка, цитата), только английскую часть до `---`, снимок модалки с маской версии; `settings/diagnostics` - «Copy diagnostics» кладёт в буфер версию, язык и выходы без адресов серверов (`SERVER_ADDRESS_PATTERN`, буфер - `grantPermissions` и `utils/readClipboard`), свитч журнала;
  - `mocksOff` - выключение моков с плашки, «нет связи», свитч в настройках выключен.
  - Про устройство сборки тесты не знают: смена webpack на другой сборщик их не трогает.
- **Всегда в Docker**: `scripts/e2e/runInDocker.ts` запускает `mcr.microsoft.com/playwright:v<версия @playwright/test>-noble` с папкой проекта в `/work`, у себя браузер Playwright не ставим. Шрифты в Windows и Linux рисуются по-разному, эталоны сняты в образе, и в CI работает тот же скрипт. Версия образа берётся из `node_modules`, поэтому обновление `@playwright/test` тянет новый образ и, скорее всего, новые эталоны (`npm run test:e2e:update`).
- **Детерминизм**: фикстура `page` (`e2e/fixtures.ts`) до загрузки кладёт в localStorage настройки с моками, английским, тёмными цветами и выключенной автопроверкой обновлений (иначе панель сходила бы в GitHub), подменяет `Math.random` генератором с постоянным зерном (`utils/installSeededRandom`: симулятор берёт случайные числа) и ставит часы на паузу (`page.clock`). Время идёт только по `page.clock.runFor`: первый опрос - в `MainLayout.open`, начало эфира - в спеке. Поэтому цифры, графики и сбой Twitch одинаковы в каждом прогоне, и масок нет.
- **Сторожа**: тест падает на ошибке в консоли, необработанном исключении и любом запросе `http(s)` (его фикстура обрывает; свой `page.route` в тесте, как в `settings/updates`, ставится позже и потому срабатывает раньше). Всегда разрешена только ошибка загрузки `obs-theme.js` (`MISSING_OBS_THEME_ERROR`: без моста файла нет, `dock.md`, «Тема из OBS»); свою ожидаемую ошибку спек задаёт `test.use({expectedConsoleError})` (`mocksOff` - отказ WebSocket на `127.0.0.1:4455`). Массив в `test.use` Playwright читает как пару «значение и опции», поэтому опция - один шаблон.
- **Не проверяет**: настоящий OBS, мост, вход и смену пароля в OBS, установку обновления и перезагрузку страницы. После `page.reload()` новая страница иногда читает localStorage до последней записи старой (гонка Chromium под нагрузкой, не панели), поэтому сохранение настроек проверяем без перезагрузки.
- **Отчёт**: `playwright-report/` (`npx playwright show-report`) со снимками, разницей и trace упавших тестов; в CI - артефакт `playwright-report` на неделю, только при падении.

## Тестовый стенд

- **Портативный OBS той же версии, что у пользователя, и локальный RTMP-сервер** в `.test-stand` (в git не попадает). Настройки пользователя, его OBS, сцены и ключи стенд не трогает, поэтому **Claude запускает его сам**: это и есть проверка в настоящем OBS.
- **Перед запуском** убеждаемся, что пользователь не стримит и не играет (нет настоящего `obs64` и тяжёлых процессов): стенд открывает окно OBS. Порт 3063 должен быть свободен: на нём тестовый сервер выпусков, и превью `dock-prod` (тот же порт) роняет шаг «Обновить» - «Проверить обновления» не находит `9.0.0`. Вопрос брандмауэра Windows можно отклонить - всё идёт через `127.0.0.1`.
- **Настоящий obs-multi-rtmp.** `setup` скачивает одну закреплённую версию плагина с GitHub (`MULTI_RTMP_VERSION` и `MULTI_RTMP_ARCHIVE` с SHA-256 в `scripts/testStand/consts.ts`, архив - в `.test-stand/downloads`) и кладёт её только в OBS стенда: архив распаковывается в его папку как есть, `obs-plugins/64bit/obs-multi-rtmp.dll` и `data/obs-plugins/obs-multi-rtmp`. Установщик плагина ставит его в `%ProgramData%\obs-studio\plugins\obs-multi-rtmp\{bin4bit, data}`, но портативный OBS 33 эту папку не читает (там же стоят плагины пользователя), а старые плагины берёт только из своих `obs-plugins/64bit` и `data/obs-plugins/<плагин>` (`frontend/plugin-manager/PluginModuleLoader_Windows.cpp` OBS); в `plugins/<плагин>/<плагин>.dll` - только плагины нового вида.
  - Трансляции стенда - с `sync-start` и `sync-stop` (поля `obs-multi-rtmp.json` в `src/output-config.cpp` плагина): плагин запускает и останавливает их вместе с основной трансляцией, поэтому `stream on|off` управляет и ими, нажимать в окне ничего не нужно. У видеонастроек - `encoder: obs_x264` и его параметры, звук плагин берёт у основной трансляции.
  - **Запасной вариант**: не скачалось или сумма не сошлась - стенд пишет `WARNING ... is not installed (<причина>)`, убирает плагин из OBS стенда и подключает в коллекцию свой скрипт `scripts/testStand/multiRtmp/fake-multi-rtmp.lua`: он, как плагин, на `OBS_FRONTEND_EVENT_STREAMING_STARTING` читает `obs-multi-rtmp.json` профиля и запускает выход с именем `multi-output` (`rtmp_output` для `RTMP`, `ffmpeg_mpegts_muxer` для `SRT_RIST`, как плагин), службой `rtmp_custom` из `service-param` и кодировщиком из `video_configs` на каждую включённую трансляцию с `sync-start`, а на `STREAMING_STOPPING` останавливает трансляции с `sync-stop`. Сценарий тогда кончается `ALL PASSED with the imitation of obs-multi-rtmp`. Нарочно - `npm run test:stand -- --fake-multi-rtmp` (и `stand -- setup --fake-multi-rtmp`), без скачивания.
  - **Новая версия плагина** - `npm run stand -- check-plugin`: сверяет закреплённую версию с последним выпуском на GitHub, при новой пишет `WARNING`, размер и SHA-256 архива из API и выходит с кодом 1 (шаг скилла выпуска). Тогда поднимаем версию и сумму, смотрим в исходниках, не поменялся ли формат `obs-multi-rtmp.json`, и прогоняем стенд.
- **`npm run test:stand`** прогоняет всё, останавливает стенд и пишет `ALL PASSED`; около 5 минут и 900 МБ на диске:
  1. Запускает и закрывает OBS, как просит установщик, раскладывает текущий код в папку с кириллицей так же, как портативный архив (`writeInstallLayout` из `scripts/packagePortable`: без записи в «Приложениях»), и настраивает OBS настоящим `configure-obs.ps1`.
  2. С настоящим плагином - по журналу OBS: загружена закреплённая версия (`[obs-multi-rtmp] version: <версия>`), плагин прочитал все трансляции и видеонастройки стенда. Затем до первого эфира проверяет пустые карточки трансляций obs-multi-rtmp по `obs-multi-rtmp.json`, который стенд кладёт в профиль (`MULTI_RTMP_CONFIG`: пять включённых трансляций и одна выключенная; трансляция «Stand copy of main» - с ключом основной трансляции `STAND_STREAM_KEY` на другом пути сервера; «Stand SRT» - по SRT на `127.0.0.1:8890` MediaMTX, ключа нет, `streamid` и `passphrase` - в адресе, как у плагина: путь `multi/srt` в MediaMTX пускает только с этим `srtPublishPassphrase`) - карточка с названием на каждую включённую трансляцию, выключенной нет, плашки «до первого эфира» нет, у моста пять отпечатков и ни одного ключа, адрес SRT обрезан до `srt://127.0.0.1:8890`, `mainKeyId` есть ещё до эфира и совпадает с `keyId` только у копии, предупреждение о том же ключе в панели одно.
  3. Вход в панель с паролем, отчёт о здоровье, поток до RTMP-сервера (трансляции плагина стартуют вместе с ним), битрейт в панели.
  4. Журнал: строки моста и панели, статистика, задержка отчёта панели после загрузки OBS (`after_loading=`), нет пароля, адресов и путей, выключение и включение.
  5. Выходы плагина с одним именем: основная трансляция снова стартует, с ней - выход `multi-output` на каждую включённую трансляцию плагина (битрейт из `video_configs`: 400, 800, 1200, 400 и 800 кбит/с у SRT, у основной - `STAND_MAIN_BITRATE`, 800). Проверка: пять путей `multi/` в MediaMTX, шесть карточек со своим битрейтом - основная и пять трансляций (каждый в пределах `PLUGIN_BITRATE_TOLERANCE` от заданного), нет предупреждения об одинаковых именах, предупреждение о том же ключе по-прежнему одно, у моста пять разных отпечатков - те же, что у трансляций до старта, у выхода SRT есть цифры и адрес `srt://127.0.0.1:8890` без `streamid` и `passphrase`, - `mainKeyId` у основного выхода и у одного выхода плагина, и ни одного ключа, названия трансляций на месте, в журнале статистика `multi-output@<отпечаток>` по каждому, ни одного ключа, адреса и пути (`JOURNAL_FORBIDDEN_TEXTS`, в том числе `srt://`) и нет `obs-multi-rtmp settings not understood`; после остановки основной трансляции останавливаются и выходы плагина.
  6. «Обновить» до `9.0.0`: скачивание, подпись, перезапуск с доком, который открывается на `SLOW_DOCK_DELAY_MS` (12 с) позже (корневой загрузчик панели стенда с задержкой, `packaging/setDockLoaderDelay`, после шага возвращается обычный), новая версия, конец пробы, отката нет.
  7. `9.0.1` со сломанной панелью: откат после перезапуска, текст в карточке.
  8. Фоновое обновление до `9.0.2` примерно через минуту после запуска.
  9. `9.0.3` с исправными мостом и панелью, но сломанным загрузчиком версии (вызывает `nil`: `error()` в OBS не бросает, `bridge.md`): фоновое обновление, перезапуск - пробу судит загрузчик `9.0.2` (`healthy-loader.txt`), панель `9.0.3` отчитывается, проба кончается; ещё перезапуск - заглушка запускает сломанный загрузчик и откатывается на `9.0.2` с отметкой в `rolled-back-version.txt`, следующий запуск открывает `9.0.2` и карточку с текстом об откате.
- **Отдельные команды - `npm run stand -- <команда>`** (без аргументов - список): `setup`, `install`, `release <версия> [--broken|--broken-loader]` (падающая панель или падающий загрузчик версии), `start`, `stop`, `status`, `stream on|off` (с ней - трансляции плагина или его замены), `check-plugin`, `update <версия>`, `open-settings`, `evaluate <выражение>`, `screenshot <файл.png>`.
  - `evaluate` и `screenshot` работают через отладочный порт Chromium, мышь и экран не нужны. `screenshot` снимает док в его настоящем размере: после `Emulation.setDeviceMetricsOverride` и снимка CEF дока оставляет страницу в подменённом размере, и `clearDeviceMetricsOverride` её не возвращает (до перезапуска OBS док занимал бы только часть окна, остальное белое).
  - После `stand -- install` и `start` панель уже подключена; `status` показывает версии, файлы обновления, текст панели и состояние потока.
- **Тестовые сборки - вне проекта**, в соседней `streamoscope-test-builds`: временная копия проекта `project-copy` (удаляется после сборки, в ней версия тестового выпуска) и свой кэш webpack `webpack-cache` (`WEBPACK_CACHE_DIRECTORY`). С `start:dev` и `build:prod` в проекте не пересекаются, папку можно удалить в любой момент, кроме работы стенда.
- **Не проверяет**: трансляции плагина по WHIP (OBS хочет для них звук в Opus, а плагин берёт звук основной трансляции), площадки выходов плагинов (у всех выходов стенда хост `127.0.0.1`, это закрывают модульные тесты `discoverTargets` и `detectPlatform`), снятую галку дока в меню Docks (нужно нажимать в окне OBS; вручную на стенде: страница панели не создаётся, `panel=0`, отката нет), настоящий GitHub и настоящий установщик - выпуски только с тестового сервера.
- **Версии OBS, RTMP-сервера и obs-multi-rtmp с SHA-256** - `scripts/testStand/consts.ts`; у пользователя вышел новый OBS - обновляем там, новый плагин - по `check-plugin`, как выше.
- **В настоящем OBS пользователя** изменение моста подхватывается так: Инструменты → Скрипты → «Перезагрузить скрипты», затем «Скопировать диагностику» в панели.

## Разработка в браузере

- **`npm run start:dev`** (`http://localhost:3062`): панель ходит в настоящий OBS и подключается сама, без пароля; не запущенный OBS подхватит, как только он поднимется.
- Компоненты обновляет React Fast Refresh. Одиночки (`obsConnectionService`, `store`, `routerManager`) отказываются от горячей замены (`import.meta.webpackHot?.decline()`): правка в них или в их импортах перезагружает страницу.
- Eslint под dev-сервером не запускается: его ошибка ломает сборку, и обновления перестают применяться. Файлы - в памяти, `build` не трогается.

## Обновление целиком тестовой сборкой

Обычно хватает `npm run test:stand`. Тестовая сборка установщика нужна, когда проверяем сам `setup.exe`; ставит её пользователь из Проводника.

- **Переменные `TEST_UPDATE_SERVER` (`http://127.0.0.1:3063`) и `TEST_UPDATE_PUBLIC_KEY` при `npm run package:installer`.**
  - Webpack подставляет `process.env.TEST_UPDATE_SERVER`, и транспорт GitHub берёт его базовым адресом вместо `https://api.github.com/repos/tjnk24/streamoscope/` (`GITHUB_BASE_URL` в `src/api/github/transport/consts.ts`); пути те же: `<сервер>/releases/latest`, `<сервер>/releases`.
  - `scripts/buildInstaller/stageTestUpdater` заменяет в `updater/Update-Widget.ps1` папки выпуска значения по умолчанию `ReleaseBaseUrl`, `LatestReleaseUrl` и `PublicKey`.
  - Без переменных сборка обычная. Подмены «на лету» в обновлятор не встраиваем, чтобы настоящую установку нельзя было перенаправить.
- **Поддельный выпуск - `npm run serve:test-release -- <папка>`** (`scripts/serveTestRelease`): `/releases/latest` (его же берёт тестовый обновлятор) и `/releases` из одного выпуска в формате GitHub API со строкой совместимости и старой датой публикации (иначе фоновая проверка ждала бы 48 ч), файлы - по `/download/v<версия>/...`, CORS открыт для `file://`; `--broken-signature` отдаёт чужую подпись архива.
  - В папку кладём подписанные `streamoscope-<версия>.zip` (верхний уровень - папка `streamoscope-<версия>`) и `compatibility.json`.
  - Тестовый ключ (`minisign -G -W`) и более новая версия (копия проекта с поднятой `version` и ссылкой на `node_modules`) - в `.test-stand`, их делает `npm run stand -- release <версия>`: `package:release` в начале удаляет всю `release/`.
  - После проверки ставим обычную сборку.
- **Обновлятор без OBS** - на черновой раскладке установки с подменённым `LOCALAPPDATA`; настоящую установку это не трогает, кроме `DisplayVersion` в реестре, поэтому в копии `consts.ps1` подменяем `UninstallRegistryKey`.
- **Тихий установщик при существующей установке ставит в её папку и игнорирует `/DIR`** (Inno берёт прежнюю папку по `AppId`). Поэтому проверки в черновой папке с подменённым `APPDATA` - только без настоящей установки, иначе обновятся её файлы (настройки OBS не тронуты: скрипт смотрит в черновой `APPDATA`).
- **Проверка без OBS пользователя**: тихая установка в черновую папку (`/DIR=`) с `APPDATA` и `LOCALAPPDATA` на копию настроек OBS, где пути `[Locations]` в `global.ini` переписаны на копию; до и после сверяются хэши настоящих файлов OBS.
